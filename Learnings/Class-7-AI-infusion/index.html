The hook

Why hand an LLM a ruler?

Ask a model “does this answer contain filler words?” and it will tell you. Ask again and it may tell you something slightly different. Ask a different model and you get a different definition of “filler” altogether.

That is fine for a chatbot. It is not fine for a hiring screen. If a candidate is rejected because their answer was “padded,” the hiring team has to be able to say what padded means — and it has to mean the same thing on Monday as it did on Friday, for every candidate.

So the design splits the work cleanly. Tools measure. The LLM explains. Three plain Python functions — filler-word counting, STAR-structure detection, keyword relevance — produce numbers the company defined. The model decides which tool to call, reads the results, and turns them into encouraging, specific feedback. It never invents the score.

Ask the room

The model can already spot filler words on its own. Why write detect_filler_words() at all?

Because the model's understanding of “filler” and the company's can drift apart — and you can't see when they do. A hard-coded list keeps the AI and the hiring team in the same ballpark: it gives the same answer every run, it can be reviewed in a pull request, and when a candidate disputes a score you can point at the exact rule. That is what “deterministic” buys you here.

The brief

Screen out the people applying only for the package

The assignment came from a company hiring AI engineers, and the class solved it live instead of taking it home. The scenario: hiring teams drown in résumés, and many applicants aren't qualified — they saw a good opening or a good salary and clicked apply. Before a résumé reaches a human, a text-based AI interview should filter them.

Given a candidate's written answer to an interview question, the system must:

  1. Evaluate the answer using a set of tools the agent chooses between.
  2. Give feedback that is encouraging when the answer is good and specific about what to fix when it isn't.
  3. Remember every question, answer and evaluation, so it can produce a final report and answer meta-questions like “how am I doing so far?”
  4. Run behind a browser interface.

It is conversational, not voice — the candidate types. Questions come from a fixed bank, so the evaluation stays comparable across candidates.

One question, two answers

Q2 behavioural ASKED “Describe a situation where you disagreed with a teammate. How did you handle it?”

At my previous companyS a teammate wanted to rewrite our payments service. I was responsibleT for its uptime, so I listened to his reasons first, then I proposedA we look at the incident data together. We agreed on a compromise — rewrite one module behind a flag — and communicated it to the team. As a resultR the outcome was a 30% drop in incidents and no big-bang rewrite.

Notice “in the end” in the weak answer. It is one of the result cues — but the weak answer still has no situation, task or action, and it hits none of the expected keywords. The tools aren't fooled by one lucky phrase, because three of them vote on different properties.

Production reality

The filler-word tool exists for a specific failure: a candidate who doesn't know the answer pads it to look long. Length alone is a terrible proxy for quality — five sentences of “basically, you know, kind of” score as long as five sentences of substance. A filler count is the cheapest possible signal that separates the two.

The asks

Four asks, one graded deliverable

Ask the room

The final report has to name the weakest area. Can the LLM just “look back” at the conversation and decide?

Only if the conversation still exists, and only if it holds something you can aggregate. Feedback prose can't be averaged. That is why ask 2 is about memory first and the report second: store the tool outputs — the numbers — and the report becomes arithmetic over a list.

Architecture

One loop, one list, two front doors

Strip away the UI and the system is small: a function that loops between the model and the tools, and a list that remembers what the tools said.

The project folder

interview-iq/ ├── .env # GROQ_API_KEY=… (never commit this) ├── requirements.txt # groq, gradio, python-dotenv ├── tools.py # ask 1 · the three deterministic tools ├── interview_bank.py # questions + expected keywords + category ├── agent.py # schemas, run_loop, session_log, report, ask_agent ├── main.py # terminal flow ├── app.py # ask 3 · Gradio UI ├── memory_check.py # ask 2 · verification script — written last ├── interviewer_agent.py # ask 4 · bonus └── run_multi_agent.py # ask 4 · bonus

Separate files are not ceremony. When a tool call fails you go straight to tools.py; when the scorecard renders wrong you go straight to app.py. That is how the solution is laid out in industry, and it is why the session insisted on it.

The build order

Wire nothing until it works alone

The most important instruction of the session wasn't about AI at all. It was about the order you build things in.

If you write three tools, plug them straight into the LLM and the output is wrong, you can't tell whether the tool is broken, the schema is wrong, or the model ignored you — and every attempt to find out burns API tokens. So the suggested approach is strictly bottom-up:

StepBuildDone when
1venv, requirements.txt, .env, one plain LLM callThe model answers “hello” — the key and provider config are proven before anything else exists.
2The three tools as standalone functionsEach returns the dict you expect for a hand-written strong and weak answer. No LLM involved.

On vibe-coding it

Using an LLM to write the code was explicitly allowed. What wasn't recommended was asking for the whole project in one prompt. You get a large, confident, sometimes-broken codebase you can't debug. Prompt one ask at a time and check each piece against the step it's meant to satisfy. You still have to read what it gave you.

Ask 1 · the tools

Three functions, each returning a dict

Every tool takes the raw answer and returns structured data, never a sentence. The model reads JSON reliably; the report needs numbers; the scorecard needs fields. A formatted string would serve none of them.

tools.py · ask 1 · run it directly to test
import re

# Deliberately small and hard-coded: the company decides what counts as filler,
# not the model. Extend the list; never hand the definition to the LLM.
FILLER_WORDS = ["um", "uh", "like", "basically", "actually", "literally",
                "you know", "kind of", "sort of", "i mean"]

STAR_SIGNALS = {
    "situation": ["when i was", "at my previous", "in my previous", "while working",
                  "at my last", "we had a"],
    "task":      ["i needed to", "my task was", "i was responsible", "the goal was",
                  "i had to", "my job was"],
    "action":    ["i decided", "i implemented", "i built", "i led", "i created",
                  "i wrote", "i set up", "i proposed"],
    "result":    ["as a result", "this led to", "which led to", "we achieved",
                  "reduced", "improved", "in the end"],
}


def _count(phrase: str, text: str) -> int:
    # \b on both sides: "um" must not match "summary", "like" must not match "likely"
    return len(re.findall(r"\b" + re.escape(phrase) + r"\b", text))


def detect_filler_words(answer: str) -> dict:
    text = answer.lower()
    found = {w: _count(w, text) for w in FILLER_WORDS}
    found = {w: n for w, n in found.items() if n > 0}
    total = sum(found.values())
    return {
        "total": total,
        "found": found,
        "verdict": "clean" if total <= 2 else "needs improvement",
    }


def check_star_structure(answer: str) -> dict:
    text = answer.lower()
    present = [part for part, cues in STAR_SIGNALS.items()
               if any(_count(cue, text) for cue in cues)]
    missing = [part for part in STAR_SIGNALS if part not in present]
    return {"present": present, "missing": missing, "all_present": not missing}


def score_relevance(answer: str, expected_keywords: list) -> dict:
    text = answer.lower()
    # plain substring on purpose: "listen" should credit "listened"
    covered = [k for k in expected_keywords if k.lower() in text]
    missed = [k for k in expected_keywords if k.lower() not in text]
    score = round(len(covered) / len(expected_keywords) * 100) if expected_keywords else 0
    return {"score": score, "covered": covered, "missed": missed}


if __name__ == "__main__":
    # Step 2: prove every tool on its own before any LLM sees it.
    weak = "Um, basically I just, like, talked to him and you know it was fine."
    print(detect_filler_words(weak))
    print(check_star_structure(weak))
    print(score_relevance(weak, ["communicat", "listen", "compromise", "data"]))
1Lists are policy, and they are deliberately incompleteThe filler list and the STAR cue lists are non-exhaustive. Extend them as you find misses. The point is that a person extends them, in a reviewed change, not that the model improvises.
2The landmine: substring countingThe obvious version is answer.lower().count("um"). It counts the “um” in summary, document and umbrella, and the “like” in likely. A careful candidate gets penalised for vocabulary. Word boundaries (\b) fix it.
3A verdict, not just a counttotal ≤ 2 is “clean”. Everyone says “um” occasionally; the threshold encodes how much the company tolerates.
4Relevance uses substrings on purposeHere the opposite choice is right: the keyword listen should credit “listened”, and communicat should credit both “communicated” and “communication”. Store stems in the bank and let the substring match do the rest.
5all_present: not missingAn empty list is falsy, so not missing is True exactly when nothing is missing. It's a small idiom that reads like the sentence it implements.

Tools the model can see: the schema

The model never sees your Python. It sees a JSON description of each tool: its name, a sentence about what it does, and the parameters it takes. The description is how the model decides whether to call it, so write it like documentation for a colleague.

agent.py · ask 1 + ask 2 · the heart of the project
import json
import os

from dotenv import load_dotenv
from groq import Groq

from tools import detect_filler_words, check_star_structure, score_relevance

load_dotenv()
client = Groq(api_key=os.environ["GROQ_API_KEY"])
MODEL = "openai/gpt-oss-20b"   # llama-3.3-70b-versatile is deprecated on Groq

# Session memory: one structured dict per evaluated answer.
# {"question", "category", "answer", "results": {tool_name: tool_output}, "feedback"}
session_log = []

TOOL_SCHEMA = [
    {"type": "function", "function": {
        "name": "detect_filler_words",
        "description": "Count filler words (um, uh, basically, you know ...) in the candidate's answer.",
        "parameters": {"type": "object",
                       "properties": {"answer": {"type": "string"}},
                       "required": ["answer"]}}},
    {"type": "function", "function": {
        "name": "check_star_structure",
        "description": "Check which parts of Situation, Task, Action, Result the answer contains.",
        "parameters": {"type": "object",
                       "properties": {"answer": {"type": "string"}},
                       "required": ["answer"]}}},
    {"type": "function", "function": {
        "name": "score_relevance",
        "description": "Score 0-100 for how many expected keywords the answer covers.",
        "parameters": {"type": "object",
                       "properties": {
                           "answer": {"type": "string"},
                           "expected_keywords": {"type": "array", "items": {"type": "string"}}},
                       "required": ["answer", "expected_keywords"]}}},
    {"type": "function", "function": {
        "name": "generate_final_report",
        "description": "Aggregate the whole session: average relevance, lowest-scoring question, weakest area.",
        "parameters": {"type": "object", "properties": {}}}},   # no arguments
]


def generate_final_report() -> str:
    if not session_log:
        return "No answers evaluated yet."
    lines, scores, gaps = [], [], {}
    for i, entry in enumerate(session_log, 1):
        r = entry["results"]
        fill = r.get("detect_filler_words", {})
        star = r.get("check_star_structure", {})
        rel = r.get("score_relevance", {})
        lines.append(f"Q{i}. {entry['question']}")
        lines.append(f"   fillers: {fill.get('total', '-')}  |  "
                     f"STAR missing: {', '.join(star.get('missing', [])) or 'none'}  |  "
                     f"relevance: {rel.get('score', '-')}/100")
        if "score" in rel:
            scores.append((rel["score"], i, entry))
        for part in star.get("missing", []):
            gaps[part] = gaps.get(part, 0) + 1
        if fill.get("total", 0) > 2:
            gaps["filler words"] = gaps.get("filler words", 0) + 1
    if scores:
        avg = sum(s for s, _, _ in scores) / len(scores)
        low_score, low_i, low = min(scores, key=lambda t: t[0])
        low_gaps = low["results"].get("check_star_structure", {}).get("missing", [])
        lines.append(f"\nAverage relevance: {avg:.0f}/100")
        lines.append(f"Lowest-scoring question: Q{low_i} ({low['category']}) at {low_score}/100")
        lines.append(f"Weakest area: {low['question']} "
                     f"- missed {', '.join(low['results']['score_relevance']['missed']) or 'nothing'}"
                     f"{'; STAR gaps: ' + ', '.join(low_gaps) if low_gaps else ''}")
    if gaps:
        ranked = sorted(gaps.items(), key=lambda kv: -kv[1])
        lines.append("Recurring gaps: " + ", ".join(f"{k} x{n}" for k, n in ranked))
    return "\n".join(lines)


TOOL_FUNCTIONS = {
    "detect_filler_words":   lambda a: detect_filler_words(a["answer"]),
    "check_star_structure":  lambda a: check_star_structure(a["answer"]),
    "score_relevance":       lambda a: score_relevance(a["answer"], a["expected_keywords"]),
    "generate_final_report": lambda a: generate_final_report(),
}

SYSTEM_PROMPT = """You are InterviewIQ, an encouraging AI mock-interview coach.
For every candidate answer:
- call detect_filler_words, check_star_structure and score_relevance
- base your feedback ONLY on what the tools return; never invent a score
- reply in 3-4 sentences: one thing that worked, one concrete fix
When asked about overall performance, use the session history you are given,
or call generate_final_report."""

MAX_TOOL_ROUNDS = 5


def run_loop(messages: list, result_out: dict | None = None) -> str:
    for _ in range(MAX_TOOL_ROUNDS):
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOL_SCHEMA, tool_choice="auto")
        msg = response.choices[0].message
        if not msg.tool_calls:                      # model is done: plain answer
            return msg.content
        messages.append({
            "role": "assistant", "content": msg.content or "",
            "tool_calls": [{"id": c.id, "type": "function",
                            "function": {"name": c.function.name,
                                         "arguments": c.function.arguments}}
                           for c in msg.tool_calls]})
        for call in msg.tool_calls:
            name = call.function.name
            args = json.loads(call.function.arguments or "{}")
            result = TOOL_FUNCTIONS[name](args)
            if result_out is not None and name != "generate_final_report":
                result_out[name] = result           # captured for session memory
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": json.dumps(result)})
    return "Sorry - I couldn't finish evaluating that answer."


def run_turn(item: dict, answer: str) -> str:
    user_message = (f"Question: {item['question']}\n"
                    f"Candidate answer: {answer}\n"
                    f"Expected keywords: {item['expected_keywords']}\n"
                    "Evaluate this answer using the available tools, then give short feedback.")
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": user_message}]
    results = {}
    feedback = run_loop(messages, result_out=results)
    session_log.append({"question": item["question"], "category": item["category"],
                        "answer": answer, "results": results, "feedback": feedback})
    return feedback


def ask_agent(user_message: str) -> str:
    history = json.dumps([{k: e[k] for k in ("question", "category", "results")}
                          for e in session_log], indent=1)
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": f"Session so far:\n{history}\n\n"
                                            f"Candidate asks: {user_message}"}]
    return run_loop(messages)


def ask_final_report() -> str:
    return generate_final_report()
1No parameters still needs a schemagenerate_final_report declares "properties": {}. In plain Python you'd never write that, but without it the model doesn't know the function can be called with nothing.
2The dispatch tableTOOL_FUNCTIONS maps the name the model asks for to a lambda that unpacks its arguments. One dictionary lookup replaces an if/elif chain, and adding a tool is one line here plus one schema entry.
3MAX_TOOL_ROUNDS = 5 is a seatbeltA model that keeps calling tools forever is a real failure mode, and every round is a paid request. Cap it, and return something graceful when the cap is hit.
4Message order is part of the protocolThe assistant message carrying the tool_calls must go into messages before the tool results, and each result carries the tool_call_id it answers. Get either wrong and the provider rejects the next request.
5Memory stores what the tools said, not what the model saidresult_out is filled inside the loop from the tool return values. The session log holds measured numbers. The model's paraphrase of them goes in feedback, next to them, never in place of them.
6The model is named in one placellama-3.3-70b-versatile was deprecated on Groq while the class ran. Swapping to openai/gpt-oss-20b, which has a generous free tier, is a one-line change. Other providers work too, but check their tool-call format, which can differ slightly.

Ask 2 · memory

A list that remembers, and arithmetic over it

Session memory here is a Python list. That was deliberate, to keep the build doable in two hours. It still has to be structured. Appending free text would make the final report impossible; appending one dict per answer makes it a loop.

session_log[1] = { "question": "Describe a situation where you disagreed…", "category": "behavioural", "answer": "Um, basically I just, like, talked to him…", "results": { "detect_filler_words": {"total": 5, "verdict": "needs improvement", …}, "check_star_structure": {"missing": ["situation","task","action","result"], …}, "score_relevance": {"score": 0, "missed": [...], …} }, "feedback": "You used a lot of filler words, which can distract…" }

From that shape, the report is three lines of arithmetic. Average relevance is the mean of every score. The lowest-scoring question is a min(). The weakest area is the lowest-scoring question together with exactly what it missed, plus a tally of recurring gaps across all answers. That tally is what makes it “based on the complete session” rather than the last answer.

Production reality

A module-level list is shared by every browser tab. session_log = [] lives once per Python process, so if two candidates use the Gradio app at the same time, their answers land in the same list and each sees the other's scores. That's fine for a single-user demo. For real users, key memory by session: Gradio's gr.State for per-tab state, or a database table keyed by session_id. The schema of each entry stays exactly the same.

Ask the room

Should the final report be written by the LLM or by a Python function?

The numbers by Python, always. Averages and minimums are not a judgement call. In this solution the report is pure code, and the model is free to narrate it when the candidate asks, by calling generate_final_report as a tool and explaining the result. The same split as everywhere else: code measures, the model talks.

app.py · ask 3 · python app.py
import gradio as gr

import agent
from interview_bank import QUESTIONS


def format_scorecard() -> str:
    if not agent.session_log:
        return "_No answers scored yet._"
    lines = ["| # | Question | Relevance | Fillers | STAR |", "|---|---|---|---|---|"]
    for i, e in enumerate(agent.session_log, 1):
        rel = e["results"].get("score_relevance", {}).get("score", "-")
        fill = e["results"].get("detect_filler_words", {}).get("total", "-")
        star = e["results"].get("check_star_structure", {})
        star_txt = "complete" if star.get("all_present") else "missing " + ", ".join(star.get("missing", ["-"]))
        lines.append(f"| {i} | {e['question'][:48]}... | {rel}/100 | {fill} | {star_txt} |")
    return "\n".join(lines)


def show(i: int) -> str:
    return f"**Question {i + 1} of {len(QUESTIONS)}** - {QUESTIONS[i]['question']}"


def on_submit(answer, q_index):
    if q_index >= len(QUESTIONS):
        return "No more questions - click **Final report**.", format_scorecard(), q_index, "Interview complete.", ""
    feedback = agent.run_turn(QUESTIONS[q_index], answer)
    nxt = q_index + 1
    display = show(nxt) if nxt < len(QUESTIONS) else "Interview complete - click **Final report**."
    return feedback, format_scorecard(), nxt, display, ""   # "" clears the answer box


def ask_coach(message):
    return agent.ask_agent(message)


def final_report():
    return f"```\n{agent.ask_final_report()}\n```"


with gr.Blocks(title="InterviewIQ") as demo:
    gr.Markdown("# InterviewIQ - AI mock interview coach")
    q_state = gr.State(0)
    question_display = gr.Markdown(show(0))
    answer_box = gr.Textbox(label="Your answer", lines=6)
    submit_btn = gr.Button("Submit answer", variant="primary")
    feedback_box = gr.Markdown()
    gr.Markdown("### Live scorecard")
    scorecard = gr.Markdown(format_scorecard())
    gr.Markdown("### Ask the coach")
    meta_box = gr.Textbox(label="e.g. How am I doing so far?")
    meta_btn = gr.Button("Ask")
    meta_reply = gr.Markdown()
    report_btn = gr.Button("Final report")
    report_box = gr.Markdown()

    submit_btn.click(on_submit, inputs=[answer_box, q_state],
                     outputs=[feedback_box, scorecard, q_state, question_display, answer_box])
    meta_btn.click(ask_coach, inputs=meta_box, outputs=meta_reply)
    report_btn.click(final_report, outputs=report_box)

if __name__ == "__main__":
    demo.launch()
1gr.State(0) holds the question indexThe state value goes in as an input and comes back out as an output. That round trip is how a Gradio app remembers anything between clicks.
2Five outputs, five return values, in orderon_submit returns feedback, scorecard, next index, next question and "". That last empty string is what clears the answer box. The order has to match the outputs=[…] list exactly.
3Defensive .get(…, "-") everywhereIf the model skipped a tool on some turn, the scorecard shows a dash instead of raising KeyError and blanking the UI. A demo that crashes on a missing key is a failed demo.

Ask 2 · verification

Prove the memory with a planted weak answer

memory_check.py is written last, once there is something to check. It feeds one strong answer and one deliberately weak answer, asks the agent about performance, and checks the weak answer was identified as the weakest area. It's a test with a known right answer, because you planted it.

memory_check.py · milestone 10 · python memory_check.py
import agent
from interview_bank import QUESTIONS

STRONG = ("When I was at my previous company, checkout failed for 2% of users. "
          "I was responsible for finding why. I decided to reproduce it locally, read the logs, "
          "found the root cause in a race condition, wrote a fix and a regression test. "
          "As a result failures dropped to zero.")
WEAK = "Um, basically I, like, just talked to him and, you know, it was kind of fine."

agent.session_log.clear()
agent.run_turn(QUESTIONS[0], STRONG)     # should score high
agent.run_turn(QUESTIONS[1], WEAK)       # deliberately weak

report = agent.ask_final_report()
reply = agent.ask_agent("What is my weakest area so far?")
print(report, "\n\nAgent says:", reply)

weak_q = QUESTIONS[1]["question"]
checks = {
    "report names Q2 as lowest-scoring": "Lowest-scoring question: Q2" in report,
    "Q2 scored below Q1": (agent.session_log[1]["results"]["score_relevance"]["score"]
                           < agent.session_log[0]["results"]["score_relevance"]["score"]),
    "agent's answer points at the disagreement question":
        any(w in reply.lower() for w in ("disagree", "teammate", "q2", "question 2")),
}
for name, ok in checks.items():
    print(("PASS " if ok else "FAIL ") + name)
expected output (abridged) Average relevance: 50/100 Lowest-scoring question: Q2 (behavioural) at 0/100 Weakest area: Describe a situation where you disagreed with a teammate… Recurring gaps: situation x1, task x1, action x1, result x1, filler words x1 PASS report names Q2 as lowest-scoring PASS Q2 scored below Q1 PASS agent's answer points at the disagreement question

The first two checks are deterministic: they test code. The third tests the model, and it can occasionally fail on wording even when the memory is fine. Keep that distinction in mind when one of them goes red.

Ask 4 · bonus

Add an interviewer that chases weak spots

The evaluator judges answers. A second agent decides what to ask next. If the candidate fumbles a technical question, the interviewer stays in technical and asks another one to probe depth. It only moves on once the candidate answers well, or the category runs out of questions.

interviewer_agent.py · bonus · the second agent
import json

import agent
from interview_bank import QUESTIONS

CATEGORIES = sorted({q["category"] for q in QUESTIONS})
PASS_MARK = 60

INTERVIEWER_PROMPT = f"""You are the interviewer. Choose the category of the NEXT question.
Rules:
- If the last answer scored below {PASS_MARK} and that category still has unasked
  questions, stay in the same category to probe depth.
- Otherwise move to a category the candidate has seen least.
Reply with exactly one word from: {", ".join(CATEGORIES)}"""


def remaining(category: str, asked: set) -> list:
    return [q for q in QUESTIONS if q["category"] == category and q["question"] not in asked]


def choose_next_question(asked: set) -> dict | None:
    if len(asked) == len(QUESTIONS):
        return None
    history = [{"category": e["category"],
                "score": e["results"].get("score_relevance", {}).get("score")}
               for e in agent.session_log]
    reply = agent.client.chat.completions.create(
        model=agent.MODEL,
        messages=[{"role": "system", "content": INTERVIEWER_PROMPT},
                  {"role": "user", "content": json.dumps(history)}],
    ).choices[0].message.content.strip().lower()
    # Never trust the hand-off blindly: validate, then fall back to any open category.
    category = reply if reply in CATEGORIES and remaining(reply, asked) else None
    if category is None:
        category = next(c for c in CATEGORIES if remaining(c, asked))
    return remaining(category, asked)[0]

print("\n" + agent.ask_final_report())
Production reality

Validate every hand-off between agents. The interviewer is asked for one word from a fixed list. Sometimes it will answer “Technical.” or “I'd suggest behavioural”, or name a category that has run out of questions. The code checks the reply against the allowed set and falls back deterministically. An agent's output is untrusted input to the next agent.

Judgement calls

Six decisions people get wrong

DecisionTempting answerWhat it should be
Who judges fillers & STARAsk the LLM. It understands language better than a list.A tool. The company's definition has to win, every time, auditably. The LLM's job is choosing tools and explaining results.
Where to start buildingThe UI, because it's what the client sees.The tools, standalone. The UI is the last layer. Bugs found bottom-up cost seconds; bugs found top-down cost tokens and hours.
What goes in memoryThe conversation transcript as one long string.One dict per answer with the raw tool outputs. You can't average a paragraph.
Counting fillerstext.count("um")Word-boundary regex. Substrings punish “summary”, “document”, “likely”.
Relevance scoringExact keyword match.Stem substrings (communicat), and accept that it's a floor, not a ceiling. A brilliant answer in different words still scores low. That's the first thing to upgrade (embeddings).
Vibe-codingOne prompt: “build the whole project”.One ask per prompt, and read the diff. You'll be reviewing AI-written code for the rest of your career, so start now.

Where it goes next

  • Semantic relevance. Embed the answer and a reference answer and use cosine similarity, so a strong answer in different words isn't scored zero. Keep keyword coverage alongside it as an explainable second signal.
  • Generated questions, bounded categories. Let the model write questions, but only from categories and seniority levels the hiring team defines, and store the expected keywords it was graded against.
  • Per-user sessions. gr.State or a sessions table keyed by id. Same entry schema.
  • Voice. Speech-to-text in front of the same pipeline. The evaluator doesn't change; fillers just get more frequent.
  • LangChain or another framework. Allowed and sensible. The session used plain Python so every moving part stayed visible.

Self-check

Eight questions before you build it yourself

Why are the three evaluators tools instead of instructions in the system prompt?

Instructions are interpreted differently run to run. Tools are code: the same answer always gets the same count, and the definition can be reviewed and changed deliberately. That keeps the AI and the hiring team in the same ballpark.

What would break if you appended the tool results to messages before the assistant message that requested them?

The provider would reject the request. Each role: "tool" message has to answer a tool_call_id that appears in a preceding assistant message's tool_calls.

Why does generate_final_report need "properties": {}?

The schema is the model's only knowledge of the function. An explicit empty object tells it the function takes no arguments and can be called directly.

What does MAX_TOOL_ROUNDS protect against?

A model that keeps requesting tools without ever producing a final answer. That's an infinite loop of paid API calls. The cap bounds cost and latency.

Why store tool outputs in session_log rather than the feedback text?

The report needs numbers to average and compare. The model's prose may paraphrase or round. Store both, but aggregate only the measured values.

Two candidates use the deployed Gradio app at once. What goes wrong?

They share the module-level session_log and the scorecards mix. Use gr.State or a database keyed by session id.

In memory_check.py, which check could fail even when the code is correct?

The third one. It inspects the model's free-text reply for words like “disagree”. The first two check deterministic code and should never flake.

In the bonus, why validate the interviewer's one-word reply?

An agent's output is untrusted input to the next stage. It may add punctuation, change case, or pick an exhausted category. Check it against the allowed set and fall back deterministically.
