Keep keys out of your code

Before talking to any model you need two boring but critical things: Python runs your project, and your secret are loaded from a file, never typed into code.

A is a plain text file of KEY=value lines. It's listed in .gitignore, so it never reaches GitHub. Every SDK (OpenAI, LangSmith, Tavily) looks for its key in an with a fixed name, such as OPENAI_API_KEY. load_dotenv() copies each line of .env into the environment, and the SDKs find their keys on their own.

01_hello_world_env_setup.py (core)
import os
from dotenv import load_dotenv

load_dotenv()

def describe_secret(name: str) -> str:
    value = os.environ.get(name)
    if not value:
        return f"{name} is missing ❌  → copy .env.example to .env"
    return f"{name} loaded ✅  (starts with {value[:8]!r}, {len(value)} characters)"

print(describe_secret("OPENAI_API_KEY"))
  1. load_dotenv() Reads .env from this folder (or a parent) into os.environ. A variable already exported in your terminal wins over the file.
  2. os.environ.get(name) Returns the value, or None if it isn't set, so a missing key gives a friendly message instead of a crash.
  3. value[:8] Shows only the first 8 characters, such as 'sk-proj-'. That tells you the key type but is useless to an attacker.
  4. len(value) A quick sanity check: a truncated paste shows up as the wrong length.
expected output

LANGSMITH_TRACING = (not set) → tracing is optional, see Script 02

Terminal output ends up in screenshots, screen recordings and logs. Print a masked prefix like this script does, and if a key ever leaks, revoke it and make a new one.

Check your understanding

Your .env file has OPENAI_API_KEY=sk-file, but you already ran export OPENAI_API_KEY=sk-shell in the terminal. Which key does the script use?

  1. sk-file, because load_dotenv() always overwrites the environment
    By default load_dotenv() does not override variables that already exist. It only fills in the missing ones.
  2. sk-shell, because a variable already in the environment wins over the file
    load_dotenv() skips any key that is already set, so the value you exported in the terminal is kept.
  3. Neither: the script crashes because the key is defined twice
    Defining a key in two places is allowed. One simply takes priority, and nothing raises an error.

Why does describe_secret print only value[:8]?

  1. Python cannot print strings longer than 8 characters
    Python prints strings of any length. The slice is a deliberate choice.
  2. The first 8 characters are the whole key
    Real keys are long, more than 100 characters here. The first 8 are just the prefix, such as sk-proj-.
  3. The prefix tells you which kind of key is loaded without exposing the secret
    Output ends up in screenshots and logs. A short prefix is enough to confirm the key type and is useless to an attacker.

Your first chain

Three building blocks appear in every later script: a prompt template, a chat model, and the pipe | that joins them into a chain.

The prompt is a template with an output contract

Every script summarises the same short biography (of Dr A. P. J. Abdul Kalam) from sample_data.py, so cloud and local models can be compared on identical input. The template has one , {information}, and a numbered list that tells the model exactly which three parts to return.

Pseudo code · 02_summary_chain_openai.py, the template
SET PROFILE_TEMPLATE to this text   // the numbered list is the output contract
    "Here is a short biography:", then a new line holding {information}
    "Using only this text, give me:", then three numbered parts
        1. A one-line headline about this person
        2. A three-bullet summary a 12-year-old would understand
        3. One question you would ask them in an interview

✦Think of it like this

A prompt template is a fill-in-the-blanks form, like a railway reservation slip. The printed parts never change; you only write in the blanks. The numbered list is the "output contract": the wording of the answer changes every run, but its shape (headline, three bullets, one question) stays the same.

View code
02_summary_chain_openai.py (core)
from langchain_core.prompts import PromptTemplate
from langchain_openai import ChatOpenAI
from sample_data import PERSON_INFORMATION

OPENAI_MODEL = os.getenv("OPENAI_MODEL", "gpt-5.6-sol")

def build_profile_chain(model_name: str):
    profile_prompt_template = PromptTemplate(
        input_variables=["information"], template=PROFILE_TEMPLATE
    )
    llm = ChatOpenAI(temperature=0, model=model_name)
    return profile_prompt_template | llm

chain = build_profile_chain(OPENAI_MODEL)
response = chain.invoke(input={"information": PERSON_INFORMATION})
print(response.text)
  1. os.getenv("OPENAI_MODEL", ...) The model name lives in .env, so you can switch models without editing code.
  2. input_variables Lists every {placeholder} the template expects.
  3. temperature=0 Asks for the most predictable answer. GPT-5.x reasoning models only allow their default, so LangChain quietly drops it there; it matters for local models.
  4. prompt | llm The pipe builds a : the output of the left side becomes the input of the right. This style is called .
  5. chain.invoke(...) Runs the whole chain once and returns an AIMessage.
  6. response.text The answer as one plain string. More on why not .content in 0.4.

Check your understanding

The template has one placeholder, {information}. Which call runs the chain correctly?

  1. chain.invoke({"information": PERSON_INFORMATION})
    The dict key matches the placeholder name, so the biography fills the blank.
  2. chain.invoke({"bio": PERSON_INFORMATION})
    The key must match the placeholder name exactly. bio is not a placeholder in this template.
  3. chain.invoke(PERSON_INFORMATION)
    The chain expects a dict of placeholder values, not a plain string.

Why does the template end with a numbered list?

  1. It makes the model reply faster, because it skips the explanation
    The list does not change the speed. It sets the shape of the answer.
  2. The model only reads numbered lists, so plain sentences would be ignored
    The model reads the whole prompt. The list works because it names the three parts to return.
  3. It is the output contract: the wording changes every run, but the shape stays the same
    The numbered list tells the model which three parts to return, so every answer has a headline, three bullets and one question.

Tracing with LangSmith, no code changes

Add the three LANGSMITH_* lines from 0.1 to .env and run any script again. LangChain notices them and sends a of every call to smith.langchain.com automatically.

  1. 1

    RunnableSequence

    The parent trace: one run of your whole chain.

  2. 2

    PromptTemplate

    A child step showing the filled-in prompt that was actually sent.

  3. 3

    ChatOpenAI or ChatOllama

    The model call, with latency, token count and cost. Compare a cloud and a local run side by side.

In Part B tracing is even more useful: you'll see two model calls with the tool call in between, which is the agent loop made visible.

Check your understanding

In the sample output, response.tool_calls is []. Why is it empty?

  1. The chain has no tools and the model asked for none, so nothing was requested
    Nothing in a plain chain can request a tool. The field is only filled when the model asks for one, which happens with the agents in Part B.
  2. OpenAI models never return tool calls
    OpenAI models do return tool calls when you give them tools. Here there are none to call.
  3. LangSmith tracing is switched off
    Tracing only records a run. It has no effect on what the response object holds.

In a LangSmith trace, which step shows the filled-in prompt that was actually sent to the model?

  1. RunnableSequence
    This is the parent step: one run of your whole chain. It does not show the prompt by itself.
  2. PromptTemplate
    It is a child step that shows the filled-in prompt that was actually sent.
  3. ChatOpenAI or ChatOllama
    This step is the model call, with latency, token count and cost.

What do you change to start tracing a script with LangSmith?

  1. Wrap every chain in a LangSmith decorator in your code
    Not needed. LangChain notices the LANGSMITH_* lines and traces the calls automatically.
  2. Replace ChatOpenAI with a LangSmith model class
    The model stays the same. Tracing is switched on from .env, not from the model.
  3. Add the LANGSMITH_* lines to .env and run the script again
    That is enough. LangChain sends a trace of every call, with no code changes.
  4. Turn on tracing in the OpenAI dashboard
    The traces come from LangChain in your script. The OpenAI dashboard does not switch them on.
0.5

From chain to agent

A model on its own can only produce text. It doesn't know today's weather, this week's news or the current price of anything. An agent fixes that by pairing the model with tools it may call.

Think of it as agent = LLM (the brain that decides) + tools (functions it may call). LangChain's create_agent(model, tools) builds the whole for you:

  1. Send the question and the list of tools to the model.
  2. If the model replies "please call tool X with arguments Y", run X(Y).
  3. Send the tool's result back to the model and repeat, until it answers in plain text.

A tool is a function with a menu card

To focus purely on the mechanics, the first script's search tool is a placeholder: whatever you ask, it returns the same weather report for Bengaluru. In 0.7 we swap in real search and nothing else changes.

01_agent_with_placeholder_tool.py (core)
from langchain.agents import create_agent
from langchain.tools import tool
from langchain_core.messages import HumanMessage
from langchain_openai import ChatOpenAI

@tool
def search(query: str) -> str:
    """Look up live information on the internet.

    Use this for anything that changes over time and that you cannot know
    from memory: today's weather, recent news, current prices, upcoming events.

    Args:
        query: What to look up, as a short search phrase.
    """
    print(f"🔎 search tool called with: {query}")
    return "Bengaluru right now: 24°C, light drizzle, humidity 78%"

llm = ChatOpenAI(model=OPENAI_MODEL)
agent = create_agent(model=llm, tools=[search])

result = agent.invoke({"messages": [HumanMessage(content=QUESTION)]})
print_agent_trace(result)
  1. @tool This turns an ordinary function into something an agent can call.
  2. search, query: str, -> str The name and become the tool's name and input schema: one text argument called query.
  3. The docstring Becomes the tool's description. It's written for the model: say clearly when the tool helps. The model decides whether and how to call it from this alone.
  4. create_agent(model, tools) Builds the loop in one line.
  5. {"messages": [HumanMessage(...)]} An agent's input is a chat-shaped list of messages. means "typed by the user".
  6. result A dict whose "messages" list is the whole conversation, tool calls included.
✦Think of it like this

The model is a customer in a restaurant who can't enter the kitchen. @tool prints a menu card: the dish name, what you need to say when ordering, and when it's a good choice. The customer only ever orders; the kitchen (LangChain) cooks and brings the plate back.

✓Test a tool without an agent

search.invoke({"query": "anything at all"}) calls it directly. search.name is "search" and search.description is the docstring text the model sees.

Check your understanding

Why does 0.5 use a placeholder search tool that returns the same report every time?

  1. It is faster than real search, so it is used in production
    The placeholder is for learning the loop. It is not meant for production.
  2. It lets you study the agent loop without depending on live web results
    Live results change, so the placeholder keeps the loop easy to follow. Section 0.7 swaps in real search.
  3. It is the only tool that works with create_agent
    create_agent accepts any tool. The placeholder is just one example.
  4. It stops the model from calling tools
    The model does call it, which is the point. The trail shows that call.

When does the agent loop stop?

  1. After the search tool has run once
    One tool call is not a stop rule. The model may call tools several times.
  2. When the tool returns an empty result
    An empty result is still sent back to the model, which then decides what to do next.
  3. When the model's reply has no tool calls, so it is plain text
    That is the stop rule. The reply then becomes the final answer.

  [2] ToolMessage  : (search) Bengaluru right now: 24°C, light drizzle, humidity 78%

  • [1]AIMessageThe model decides to call a tool. Its text is empty and its tool_calls list holds the request. Notice the model wrote the query "Bengaluru weather now" itself.

  • [3]AIMessageNo tool calls this time, so it's the final answer.
Pseudo code · agent_trace_printer.py (core)
DEFINE _one_line(text, limit = 160):
    SET flat = text with all whitespace squashed onto one line
    IF flat has at most limit characters THEN RETURN flat
    RETURN the first limit characters of flat, plus how many characters were cut

DEFINE print_agent_trace(result):
    SET messages = result["messages"]
    FOR EACH message, with its index:
        SET kind = the class name of message
        SET tool_calls = message.tool_calls, or an empty list
        IF tool_calls is not empty THEN
            FOR EACH call in tool_calls:
                PRINT index, kind, "tool call" and the call name with its arguments, cut to 120 characters
        ELSE IF kind is ToolMessage THEN
            PRINT index, kind, the tool name and the result, on one line
        ELSE
            PRINT index, kind and the message text, on one line
    PRINT the text of the last message   // the final answer

agent_trace_printer.py (core)
def _one_line(text: str, limit: int = 160) -> str:
    flat = " ".join(str(text).split())
    if len(flat) <= limit:
        return flat
    return f"{flat[:limit]} … (+{len(flat) - limit} chars)"

def print_agent_trace(result: dict) -> None:
    messages = result["messages"]
    for index, message in enumerate(messages):
        kind = type(message).__name__
        tool_calls = getattr(message, "tool_calls", None) or []
        if tool_calls:
            for call in tool_calls:
                print(f"  [{index}] {kind:<13}: 🛠  tool call → {call['name']}({_one_line(call['args'], 120)})")
        elif kind == "ToolMessage":
            print(f"  [{index}] {kind:<13}: ({message.name}) {_one_line(message.text)}")
        else:
            print(f"  [{index}] {kind:<13}: {_one_line(message.text)}")
    print(messages[-1].text)
  1. _one_line() Squashes text onto one line and cuts it at 160 characters, so long search results don't flood the terminal.
  2. type(message).__name__ The class name: HumanMessage, AIMessage or ToolMessage.
  3. getattr(..., "tool_calls", None) or [] Only AI messages have tool_calls; this safely gives an empty list for the rest.
  4. for call in tool_calls One AI message can request several tools at once, so each gets its own line with the same index.
  5. messages[-1].text The final answer is simply the text of the last message.

Structured output

Free text is great for people but painful for programs: which part of this paragraph is the link? With response_format, the agent must also return its answer as data that matches a schema you define.

Pseudo code · 04_agent_with_structured_output.py (core)
DEFINE class Source: a web page the answer is based on
    title: text, a short title such as the event name
    url: text, the full link, starting with https://

DEFINE class AgentAnswer: the agent's final reply
    answer: text, the answer in plain words
    sources: a list of Source, empty when nothing is cited

CREATE agent = create_agent with model llm, the TavilySearch tool and response_format AgentAnswer
SET result = agent.invoke with the question as a HumanMessage
SET structured = result["structured_response"]   // a validated AgentAnswer
FOR EACH source in structured.sources:
    PRINT source.title and source.url
Imported
  • BaseModel from pydantic: the base class that describes a data shape and checks it.
  • Field from pydantic: adds a description to a field, which the model reads as an instruction.
View code
04_agent_with_structured_output.py (core)
from pydantic import BaseModel, Field

class Source(BaseModel):
    """A web page the answer is based on."""
    title: str = Field(description="Short title of the page, e.g. the event name")
    url: str = Field(description="Full link to the page, starting with https://")

class AgentAnswer(BaseModel):
    """The agent's final reply: a readable answer plus the pages it used."""
    answer: str = Field(description="The answer to the user's question, in plain text")
    sources: list[Source] = Field(default_factory=list,
                                  description="Every web page used to write the answer")

agent = create_agent(model=llm, tools=[TavilySearch()], response_format=AgentAnswer)

result = agent.invoke({"messages": [HumanMessage(content=QUESTION)]})
structured: AgentAnswer = result["structured_response"]
for source in structured.sources:
    print(source.title, source.url)
  1. BaseModel A class describes the shape of the data you want back, and validates it.
  2. Field(description=...) Like tool docstrings, class docstrings and field descriptions are sent to the model. They're instructions.
  3. list[Source] Schemas can nest: an answer holds a list of sources, each with a title and URL.
  4. default_factory=list An empty list if the agent cites nothing, instead of an error.
  5. response_format=AgentAnswer The only change compared with Script 03.
  6. result["structured_response"] A new key holding a validated AgentAnswer. The usual "messages" trail is still there.

Check your understanding

Why read result["structured_response"] instead of parsing the last message yourself?

  1. The last message is always the user's question
    The last message is a reply from the model or a tool, not the question.
  2. The result has no messages list, so this is the only field left
    The messages trail is still there. The structured answer is a separate key next to it.
  3. It is already a validated AgentAnswer object, so you need no parsing
    The last message is text, or a tool message, that you would have to parse yourself. The structured key already holds the checked object.
  4. The agent deletes the messages when it finishes
    The messages list is kept. The structured answer is added to the result beside it.

What does Field(description=...) do in the schema?

  1. It is sent to the model as an instruction for filling that field
    Like tool docstrings, field descriptions are read by the model when it writes the answer.
  2. It checks that the URL opens in a browser
    Field does not open links. The description is text for the model.
  3. It sets the default value of the field
    A default comes from an argument such as default_factory, not from the description.
  4. It is only a comment for you, and the model never sees it
    The description is sent to the model, so it shapes the answer.

Recap and self-check

You've revised the two foundations every lesson builds on: a chain that turns a prompt into an answer, and an agent that loops over tool calls until it can answer.

Keys live in .env and reach the SDKs through environment variables. A chain is prompt | llm; swapping ChatOpenAI for ChatOllama changes one line. The answer comes back as an AIMessage: read .text, count cost in usage_metadata, and watch tool_calls. An agent adds tools described by their name, type hints and docstring; LangChain runs them, and the trail of Human, AI, Tool and AI messages shows every step. A vendor tool like TavilySearch offers the model richer options, and response_format turns the final answer into a validated Pydantic object.
