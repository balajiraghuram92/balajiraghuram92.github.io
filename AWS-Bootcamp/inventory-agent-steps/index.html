Build an inventory planning agent, one idea at a time

Eight short Python files. Each one adds a single new idea on top of the last: a SQL database, embeddings, a vector database, a prompt chain, RAG, tool calling, a fixed pipeline, and finally a chat app that answers "Should I reorder SKU-002?" with real numbers. This page walks through every file, block by block.

The code is the starter code from Module 4 of Shivank Agarwal's workshop Hands-On: RAG and Tool Calling. Most files have small TODO gaps for you to fill; this page explains each gap and shows one way to fill it.

1

What you will build

A chat assistant for a shop or warehouse planner. You ask about a product; it looks up the facts, does exact maths, and gives advice.

By the end (step 08) you can type questions like these into a browser window. They are the example prompts written in the app itself:

  • What is the reorder quantity for SKU-001?
  • Should I reorder SKU-002? It's a pharma product.
  • Which SKUs are most at risk of stockout?

A SKU (stock keeping unit) is one product line you sell, for example "Paracetamol 500mg". A stockout means you have run out of it.

💡 The key idea: give each job to the right worker

JobWho does itWhy
Remember facts about each product (stock, supplier, demand)SQLite, a SQL databaseFacts are structured rows and columns. SQL gives exact answers, never "roughly".
Remember know-how (formulas, rules of thumb for pharma, electronics …)ChromaDB, a vector databaseKnow-how is free text. A vector database finds notes by meaning, not exact words.
Do the arithmetic (safety stock, reorder quantity)Python toolsPython is always right at maths. An LLM can make arithmetic slips.
Understand the question, pick the next step, explain the answerThe LLM (OpenAI model)Language and judgement are what LLMs are good at.

🔧 Analogy: a small planning office

The filing cabinet (SQLite) holds one card per product. The bookshelf (ChromaDB) holds the planning handbook. The calculator (tools) does the sums. The planner (LLM) reads your question, pulls the right card, checks the handbook, uses the calculator and writes you a short note. Nobody does a job they are bad at.

STEP 01

SQLite basics: store and query inventory data

Goal from the docstring: keep structured data (products, suppliers) in a real SQL database and read it back.

Open a database

);

💡 Keys in plain words

A primary key is a column whose value is unique for each row, like a roll number. Here sku_id is the primary key of both tables. A foreign key says "this column points to a row in another table": each supplier row belongs to one product. Lead time (lead_time_days) is the number of days between placing an order and receiving it. It is the most important number in stock planning.

Embeddings basics: find the most relevant passage

No database and no LLM yet: just an embedding model and numpy.

Turn text into vectors

02_embeddings_basics.py · lines 25–32runs locally
# Free local model: every text -> 384 numbers
model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

print("Embedding passages...")
# normalize_embeddings=True makes every vector length 1,
# so cosine similarity becomes a simple dot product
passage_vectors = model.encode(PASSAGES, normalize_embeddings=True)
print(f"Passage matrix shape: {passage_vectors.shape}  (6 passages x 384 numbers)\n")

💡 What an embedding is

An embedding is a list of numbers that stands for the meaning of a text. This model, all-MiniLM-L6-v2, turns any text into 384 numbers. Texts with similar meaning get similar lists, even when they share no words. So the six passages become a 6 × 384 table of numbers, as the print line says.

normalize_embeddings=True scales every vector to length 1. Then cosine similarity (how closely two vectors point the same way, from −1 to 1) is just the dot product: multiply the numbers pair by pair and add them up.

])

💡 The stock formulas, exactly as written here

  • Safety stock = Z × demand_std_dev × √lead_time_days. Extra units kept as a cushion, in case demand is higher than usual while you wait for a delivery.
  • Desired stock = (avg_daily_demand × lead_time_days) + safety stock. Enough to cover normal sales during the lead time, plus the cushion.
  • Demand std dev (standard deviation) measures how much daily sales bounce around the average. Steady sales → small number; jumpy sales → big number.
  • Service level is the chance of not running out during a lead time. Z is how many standard deviations of cushion that needs: 90% → 1.28, 95% → 1.65, 97% → 1.88, 98% → 2.05, 99% → 2.33.

Why √lead time? Daily ups and downs partly cancel out. Over L days the total wobble grows with √L, not L: 4 days of uncertainty is 2× one day's, not 4×.

A prompt template is a message with blanks like {sku_id} filled in on every call. The "system" message sets the role and rules; the "human" message carries this SKU's numbers. The prompt asks the model to end with DESIRED_STOCK: <number> so a program could read the number later.

Tool 1: safety stock

Z_TABLE = {90: 1.28, 91: 1.34, 92: 1.41, 93: 1.48, 94: 1.55, 95: 1.65, 96: 1.75, 97: 1.88, 98: 2.05, 99: 2.33}


# ── Tools ─────────────────────────────────────────────────────────────────────
@tool
def calculate_safety_stock(demand_std_dev: float, lead_time_days: float, service_level_pct: float) -> float:
    """
    Calculate safety stock (extra buffer units).
    safety_stock = Z * demand_std_dev * sqrt(lead_time_days)
    Z-scores: 90%->1.28, 95%->1.65, 97%->1.88, 98%->2.05, 99%->2.33
    """
    z = Z_TABLE.get(round(service_level_pct), 1.65)
    return round(z * demand_std_dev * math.sqrt(lead_time_days), 2)

💡 What @tool does

The @tool decorator turns a normal Python function into a LangChain tool. It reads the function name, the type hints (float, str) and the docstring, and turns them into a description the LLM can read: "there is a tool called calculate_safety_stock, it needs these three numbers, it does this". The docstring is the instructions for the LLM, so write it carefully.

The maths: look up Z for the rounded service level (falling back to 1.65 if it is not in the table), then round(z * demand_std_dev * math.sqrt(lead_time_days), 2).

Quick quiz

1. Why is product stock kept in SQLite and not in ChromaDB?

Stock levels are exact, structured facts. SQL returns exactly the row you ask for. ChromaDB finds text that is similar in meaning, which is right for notes and rules but wrong for "how many units of SKU-005 do we have".

2. In step 02, why is the dot product enough to measure similarity?

Because normalize_embeddings=True makes every vector length 1, and for length-1 vectors the dot product equals the cosine similarity.

3. What does where={"topic": "formula"} do in step 03?

It limits the search to documents whose metadata has topic equal to "formula". Similarity ranking then happens only among those.

4. Safety stock for 99% service, std dev 1.0, lead time 30 days?

Z = 2.33, so 2.33 × 1.0 × √30 ≈ 2.33 × 5.477 ≈ 12.76. That is SKU-005 in step 08.

5. In the agent loop, how does the code know the LLM has finished?

The reply has no tool_calls. Then response.text is the final answer. MAX_STEPS stops it if that never happens.

6. What is tool_call_id for?

It links each ToolMessage result to the tool call that asked for it, so the LLM knows which result belongs to which request, even when it asked for several tools at once.

7. Step 07 uses tools but is not an agent. Why?

Our Python code calls the tool and the two chains in a fixed order. The LLM never chooses what happens next; it only writes text.

8. Why does step 08 use math.ceil for the reorder quantity?

You order whole units, and rounding down could leave you just short of the desired stock. Rounding up keeps you at or above it.

               l.lead_time_days, l.supplier_name,
               d.avg_daily_demand, d.demand_std_dev
        FROM inventory i
        JOIN lead_time l ON l.sku_id = i.sku_id
        JOIN demand    d ON d.sku_id = i.sku_id
        WHERE UPPER(i.sku_id) = UPPER(?)
    """, (sku_id,)).fetchone()
    return dict(row) if row else None


def list_skus() -> list[dict]:
    rows = cur.execute("SELECT sku_id, sku_name, category, current_stock FROM inventory ORDER BY sku_id")
    return [dict(r) for r in rows.fetchall()]
