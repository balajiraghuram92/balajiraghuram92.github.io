Lesson 22 · Hands-on code explainer · Tool calling basics

Tool calling: letting the model ask your Python code for help

LLMs are good with words but can slip on exact maths and cannot see your data. With tool calling, the model asks your code to run a function, and answers with the real result. You will build it three times: by hand with the OpenAI SDK, with LangChain, and as a four-tool warehouse assistant.

OpenAI SDKJSON Schema toolsLangChain @toolbind_tools4 inventory tools
1

What you'll achieve

💡 The problem

An LLM (large language model, like GPT) writes text by predicting the next word. That makes it great with words, but shaky with exact work: precise maths, or looking up today's stock count in your warehouse. It may give an answer that sounds right and is slightly wrong, and it cannot see your data at all.

💡 The fix: tool calling

Tool calling lets the model ask your Python code to do the job. You describe your functions to the model (a "menu"). When a question needs one, the model does not answer. It replies with a request: "please call square_root with number = 144". Your code runs the real function, sends the result back, and the model writes the final answer using it.

The model never runs anything itself. It only asks. Your code decides whether and how to run it.

By the end of this lesson you will be able to:

  • write a tool "menu" by hand in OpenAI's JSON format and run the 4-step loop with the plain OpenAI SDK (file 1);
  • do the same thing in far fewer lines with LangChain's @tool and bind_tools (file 2);
  • give a model four warehouse tools and watch it pick the right one and fill in the arguments from a plain-English question (file 3).

🔧 Analogy: the waiter and the kitchen

The model is a waiter. It talks to the customer well, but it does not cook. The tool menu tells it which dishes the kitchen can make. When a customer orders, the waiter writes a ticket ("square_root, number 144") and passes it to the kitchen (your code). The kitchen cooks and hands back the plate (the result), and the waiter serves it with a friendly sentence.

2

The big picture: one question, four steps

All three files follow the same loop. Only the amount of code you write by hand changes.

Arrows 1 and 3 (right) are API calls to OpenAI. Arrow 3 (left) is plain Python on your machine.

🗣 The four steps, as file 1's docstring puts them

  1. We send the question plus a description of our tools (a JSON "menu").
  2. The LLM replies with either a normal answer or "please call tool X with arguments Y".
  3. Our code runs the Python function and sends the result back (with role = "tool").
  4. The LLM writes the final answer using that result.

💡 Two calls to the model, not one

When a tool is used, your code calls the model twice: once to get the tool request, once (with the result added) to get the answer. The model has no memory between calls, so the second call must carry the whole conversation so far: the question, the model's own tool request, and the tool's result. That is what the messages list is for.

1.2

The real Python function and the tool map

1_tool_calling_from_scratch.py · lines 32–39
def square_root(number: float) -> float:
    if number < 0:
        raise ValueError("Cannot compute square root of a negative number.")
    return math.sqrt(number)


# Maps the tool NAME the LLM will use -> the Python function we run
tool_map = {"square_root": square_root}

This is an ordinary function. Nothing about it is special to AI. It even refuses negative numbers with a ValueError.

tool_map is a dictionary from a name (a string) to the function itself. Later the model will say "call square_root", and we use tool_map["square_root"] to find the function to run.

🔧 Analogy: the order ticket and the recipe book

The model writes a dish name on a ticket. tool_map is the kitchen's recipe book: look up the name, get the recipe (the function), cook it.

1.4

Step 1 and 2: ask, then check for a tool request

1_tool_calling_from_scratch.py · lines 51–67
def chat_with_tools(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]

    # Step 1: ask the LLM, and tell it which tools exist.
    # reasoning_effort="none" is required for tool calling with this model in the Chat Completions API.
    response = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        tools=tools,
        reasoning_effort="none",
    )
    message = response.choices[0].message
    messages.append(message)  # keep the assistant's reply (including its tool requests) in the history

    # Step 2: did the LLM ask for a tool?
    if not message.tool_calls:
        return message.content  # no tool needed, e.g. "What is the capital of France?"
  • messages is the conversation so far, as a list. Each message has a role: "user" (the person), "assistant" (the model) or "tool" (a tool result).
  • tools=tools attaches the menu to this call. Without it the model does not know the tool exists.
  • reasoning_effort="none": the file's comment says this is required for tool calling with this model in the Chat Completions API.
  • response.choices[0].message is the model's reply. We append it to messages straight away, including its tool requests. The second call needs to see them.
  • message.tool_calls is empty when the model just answered. Then we return message.content (the text) and we are done in one call.

💡 What a tool request looks like

Each item in message.tool_calls has three things you need: an id (a unique label for this request), function.name (which tool), and function.arguments (a JSON string such as {"number": 144}, not a dict yet).

⚠️ Why the id matters

The model can ask for several tools in one reply. When you send results back, each one carries the tool_call_id of the request it answers, so the model can match result to request. A result with a wrong or missing id is rejected by the API.

For every request the model made, your code must:

  1. read the name from tool_call.function.name;
  2. turn the argument string into a dict with json.loads(...), e.g. {"number": 144};
  3. run the function: tool_map[name](**args). The ** unpacks the dict into keyword arguments, so it becomes square_root(number=144);
  4. append a "tool" message with the matching tool_call_id and the result as a string.

Then call the model again with the longer messages list. This time it can see the result and writes the answer.

⚠️ Content must be text

math.sqrt(144) returns the float 12.0. The API wants message content as a string, hence str(result).

⚠️ One round only

This function asks for tools once, then expects an answer. If the model asked for another tool in the second reply, this code would not run it. A real agent keeps looping until there are no more tool calls. Lesson 23 builds that loop.

💡 The docstring is now a prompt

In file 1 you wrote the description in JSON. Now the docstring is the description. Write it for the model to read: what the tool does and when to use it.

After @tool, square_root is a tool object, not a plain function. It has .name, .description and .args, and you run it with .invoke(...). That is why tool_map = {t.name: t for t in tools} works now.

🌍 Why the trap question matters

The file's own comment says: 123456 squared is 15241383936, not 15241383937. The two numbers differ by 1 in eleven digits, exactly the kind of thing a model can get wrong by "feel". With the tool, Python does the maths: math.sqrt(15241383937) is 123456.00000405003, which is not a whole number, so the honest answer is "no".

⚠️ The model still decides

The model chooses whether to call the tool, and what number to pass. It might pass 15241383937 to square_root, or answer from memory. Tool calling makes correct answers possible; good descriptions and prompts make them likely.

The three ready-made tools

Tool 1 · get_stock_level

3_inventory_tools_demo.py · lines 38–46
@tool
def get_stock_level(sku: str) -> str:
    """Return current stock level and reorder point for a given SKU."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    status = "LOW" if item["stock"] <= item["reorder_point"] else "OK"
    return f"{item['name']} ({sku}): stock={item['stock']}, reorder_point={item['reorder_point']}, status={status}"

sku.upper() accepts "sku-003" as well as "SKU-003": models do not always copy text exactly. An unknown SKU returns a message instead of crashing, so the model can tell the user.

Tool 2 · calculate_reorder_quantity

3_inventory_tools_demo.py · lines 49–69
@tool
def calculate_reorder_quantity(sku: str, lead_time_days: int = 7) -> str:
    """Calculate recommended reorder quantity for a SKU given supplier lead time in days."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    daily = DAILY_DEMAND.get(sku, 1)
    # Simple rule of thumb:
    #   demand during delivery wait  = daily demand x lead time
    #   safety buffer                = the same amount again (in case of delays / spikes)
    #   order                        = (wait demand + buffer) - what we already have
    lead_time_demand = daily * lead_time_days
    safety_buffer = lead_time_demand
    reorder_qty = max(lead_time_demand + safety_buffer - item["stock"], 0)
    total_cost = reorder_qty * item["unit_cost"]
    return (
        f"{item['name']} ({sku}): recommend ordering {reorder_qty} units "
        f"(lead_time_demand={lead_time_demand}, safety_buffer={safety_buffer}, "
        f"lead_time={lead_time_days}d, estimated_cost=Rs {total_cost:,})"
    )

The rule of thumb in the comments, in plain words:

  • demand while we wait for delivery = daily demand × lead time;
  • safety buffer = the same amount again, in case of delays or spikes;
  • order = (wait demand + buffer) − stock we already have, never below 0 (max(..., 0)).

lead_time_days: int = 7 has a default. If the user does not mention a lead time, the model can leave it out and 7 days is used. The :, in {total_cost:,} adds thousands separators (612,500).

Quick quiz

1. Does the model run your Python function?

No. It only replies with a request (tool name + arguments). Your code runs the function and sends the result back.

2. What does the model actually see about your tool?

Only the menu: the name, the description and the parameter schema. Never your Python code.

3. Why do we append the assistant's reply to messages before running the tool?

The second API call must contain the tool request, so the tool result that follows it has something to answer. The model has no memory between calls.

4. What is tool_call_id for?

It links each tool result to the request it answers, which matters when the model asks for several tools at once.

5. In file 1, why json.loads, and why not in file 2?

The OpenAI SDK gives arguments as a JSON string. LangChain parses them for you, so tc["args"] is already a dict.

6. What does @tool use to build the description?

The function's docstring. The name comes from the function name and the parameters from its type hints.

7. For "order SKU-003 with a 10-day lead time", what does calculate_reorder_quantity recommend?

35 units: 2 per day × 10 = 20, plus a 20 buffer = 40, minus 5 in stock = 35, costing Rs 612,500.

8. What happens in these files if the model needs a second round of tools?

Nothing runs it: the code makes one tool round and then asks for the answer. A full agent loop (Lesson 23) keeps going until no tools are requested.

# ----------------------------------------------------------------------------
# A tiny "database" (a Python dict) of warehouse items. SKU = Stock Keeping Unit = product id.
# reorder_point = when stock falls to this level or below, we should order more.
# ----------------------------------------------------------------------------
INVENTORY = {
    "SKU-001": {"name": "Industrial Valve", "stock": 120, "reorder_point": 50,  "unit_cost": 7000},
    "SKU-002": {"name": "Hydraulic Pump",   "stock": 18,  "reorder_point": 25,  "unit_cost": 35000},
    "SKU-003": {"name": "Conveyor Belt",    "stock": 5,   "reorder_point": 10,  "unit_cost": 17500},
    "SKU-004": {"name": "Safety Helmet",    "stock": 300, "reorder_point": 100, "unit_cost": 1000},
    "SKU-005": {"name": "Pressure Gauge",   "stock": 42,  "reorder_point": 40,  "unit_cost": 4500},
}

# How many units of each item we use per day (on average)
DAILY_DEMAND = {"SKU-001": 8, "SKU-002": 3, "SKU-003": 2, "SKU-004": 15, "SKU-005": 6}


# ----------------------------------------------------------------------------
# Tools. The docstring is what the LLM reads to decide WHICH tool to use, so it must be clear.
# ----------------------------------------------------------------------------
@tool
def get_stock_level(sku: str) -> str:
    """Return current stock level and reorder point for a given SKU."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    status = "LOW" if item["stock"] <= item["reorder_point"] else "OK"
    return f"{item['name']} ({sku}): stock={item['stock']}, reorder_point={item['reorder_point']}, status={status}"


@tool
def calculate_reorder_quantity(sku: str, lead_time_days: int = 7) -> str:
    """Calculate recommended reorder quantity for a SKU given supplier lead time in days."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    daily = DAILY_DEMAND.get(sku, 1)
    # Simple rule of thumb:
    #   demand during delivery wait  = daily demand x lead time
    #   safety buffer                = the same amount again (in case of delays / spikes)
    #   order                        = (wait demand + buffer) - what we already have
    lead_time_demand = daily * lead_time_days
    safety_buffer = lead_time_demand
    reorder_qty = max(lead_time_demand + safety_buffer - item["stock"], 0)
    total_cost = reorder_qty * item["unit_cost"]
    return (
        f"{item['name']} ({sku}): recommend ordering {reorder_qty} units "
        f"(lead_time_demand={lead_time_demand}, safety_buffer={safety_buffer}, "
        f"lead_time={lead_time_days}d, estimated_cost=Rs {total_cost:,})"
    )

    days = item["stock"] / daily
    return f"{item['name']} ({sku}): {days:.1f} days until stockout (stock={item['stock']}, daily_demand={daily})"
