Chunking and HyDE: how you cut a document decides what RAG can find

Before a RAG system can search a long document, it cuts it into small pieces called chunks. In this notebook you cut the same text four different ways, watch how the search results change, and then try HyDE: a trick where an LLM writes a fake answer first, and you search with that instead of the question.

Every cell is shown and explained, with the TODOs you fill in and one possible answer for each.

LangChain text splittersOpenAI embeddingsChromaSemanticChunkerBM25gpt-6-luna
1

What you will achieve

By the end you can pick a chunking strategy for a document and explain why, and you know when HyDE is worth an extra LLM call.

  • Cut one article into chunks of 50, 150 and 400 characters and see which size gives the clearest search results.
  • Try three ways of deciding where to cut: every N characters, where the meaning changes, and at Markdown headings.
  • Search a small shoe catalogue with and without HyDE, and see the results change.

💡 Why chunking matters so much

RAG (Retrieval-Augmented Generation) means: find the pieces of your documents that match a question, then give those pieces to an LLM so it can answer from them. The search never sees the whole document. It only sees chunks. So:

  • If an answer is split across two chunks, the search may find only half of it.
  • If one chunk holds five topics, it matches a question about any of them only weakly.
  • Whatever you cut badly at indexing time, no clever prompt can fix later.

💡 What HyDE is, in one paragraph

HyDE stands for Hypothetical Document Embeddings. Questions and documents are often written in different words: a shopper says "running shoes", the catalogue says "trainers" and "Pegasus". HyDE asks an LLM to imagine a good answer first. That fake answer is written in document-style words, so searching with it finds the real documents. The fake answer is never shown to the user; it is only used to search.

🔧 Analogy: cutting a textbook into flashcards

Imagine turning a textbook into flashcards for a quiz. Cards with half a sentence each are useless. Cards with a whole chapter each are too vague to find the one fact you need. One idea per card works best. Chunking is choosing how to cut those cards, and the search engine can only ever hand you whole cards.

  1. Download the lesson folder (use the "Download all" button in the box at the top of this page). It holds chunking_strategies.ipynb, requirements.txt and .env.example.

Either way, the key is never written inside the notebook itself. The cell then prints API key loaded: True or False.

PART 2.1

Finding a good chunk size

Cut one article three ways (50, 150, 400 characters), store each version in its own vector database, and ask all three the same question.

Step 1 · Cut the article into chunks

chunking_strategies.ipynb · cell 3 · split at three sizesruns locally
---
## 2.1 Finding a good chunk size
We cut the same short article into chunks of **50**, **150** and **400** characters,
store each version in its own vector database, and ask the same question to all three.

* Too small → each chunk is a fragment, the answer is spread over many pieces
* Too large → one chunk holds many topics, the match is blurry
* Just right → one chunk holds one complete idea

💡 What is going on

  • A LangChain Document is just text (page_content) plus a dictionary of labels (metadata). The label "source": "heart_article" is copied onto every chunk, so you always know where a chunk came from.
  • chunk_size is the maximum length of one chunk, counted in characters (letters, spaces and punctuation), not words or tokens.
  • chunk_overlap is how many characters the end of one chunk shares with the start of the next. The hint uses 10% of the size: 5, 15 and 40 characters.
  • RecursiveCharacterTextSplitter tries to cut at the "nicest" place first. It tries paragraph breaks ("\n\n"), then line breaks ("\n"), then spaces, and only cuts inside a word if nothing else fits. That is why it's the usual default.

Overlap: the yellow strips appear in two chunks, so a sentence cut at the edge still appears whole in at least one of them.

💡 What is going on

  • An embedding is a list of numbers that stands for the meaning of a text. text-embedding-3-small gives 1,536 numbers per text. Texts with similar meaning get similar numbers.
  • Chroma is a vector database: it stores each chunk next to its embedding and can quickly find the ones closest to a new embedding. Without a save folder, it lives in memory and disappears when the notebook stops.
  • A collection is one named table inside Chroma. Using f"heart_chunks_{size}" keeps the three sizes apart, so the comparison is fair.
  • ids give each chunk a fixed name like 150-0. If you run the cell twice, Chroma overwrites the same ids instead of storing every chunk twice (which would fill your results with duplicates).

🌍 In real projects

There is no single "right" size. Short, factual text (FAQs, product data) likes small chunks. Long reasoning (contracts, manuals) needs bigger ones. Teams test a few sizes on real questions, exactly like this cell does, and keep the one that finds the right chunk most often. Real systems usually measure size in tokens and use something like 200 to 1,000 tokens, because their documents are much longer than this toy article.

⚠️ Watch out

The best size here (150 characters) is about this tiny 600-character article. Don't copy it to your own documents; test your own.

💡 What is going on

  • textwrap.dedent removes the spaces at the start of every line (they are there only because the text is indented inside the Python code). Without it, the headings would start with spaces instead of #, and Part 2.4 could not find them. .strip() removes the blank first and last lines.
  • separator="" means "any place is a fine place to cut". So the splitter makes 100-character pieces and happily cuts in the middle of a word.
  • split_text works on a plain string and returns plain strings. (split_documents in 2.1 works on Documents and keeps their metadata.)

✎ What to look for

The printout uses repr(), which shows quotes and \n so you can see exactly where each chunk starts and ends. Look for words broken in half between two chunks.

**Look at the output:** with size 50 the answer is chopped into fragments; with size 400 the whole
article comes back as one block. Size 150 usually gives the cleanest, most focused answer for this text.

💡 What changes

With separator="\n" the splitter first breaks the text into lines, then packs whole lines into chunks of up to 200 characters, with up to 20 characters of overlap. No word is broken. If one line alone is longer than 200 characters, it is kept whole and you get a warning, because the splitter has nowhere else to cut.

🔧 Analogy: cutting a loaf of bread

Pure fixed length is a bread slicer set to 1 cm: fast and even, but it doesn't care where the raisins are. Cutting at line breaks is slicing only between rolls in a tray: still simple, but you never cut through one.

⚠️ Watch out

Fixed-length chunks ignore meaning. A heading can end up at the bottom of one chunk while its paragraph starts the next, so a search for that topic finds a chunk with the heading but not the content.

PART 2.3

Semantic chunking: cut where the meaning changes

Instead of counting characters, embed every sentence and cut where one sentence is far in meaning from the next.

chunking_strategies.ipynb · cell 8 · TODO 5: SemanticChunkerneeds OpenAI key
---
## 2.2 Fixed-length chunking
The simplest strategy: cut every N characters.
We use a small Markdown article about Machine Learning for parts 2.2 to 2.4.

💡 How SemanticChunker decides

  1. It splits the text into sentences (at full stops, question marks and exclamation marks).
  2. It embeds each sentence (together with its neighbours, to smooth things out).
  3. It measures how different each sentence is from the next one.
  4. Where the difference is unusually big (by default, bigger than 95% of all the gaps in the text), it cuts. That is a "topic jump".

create_documents([text]) takes a list of strings and returns Documents, one per chunk. There is no chunk_size: chunks are as long as the topic is.

Stuck? One possible answer for TODO 5 (not in the notebook: try it yourself first)
possible answer · TODO 5your answer
semantic_chunker = SemanticChunker(OpenAIEmbeddings(model="text-embedding-3-small"))
docs = semantic_chunker.create_documents([text])

✎ What to look for

Count the chunks and compare them with 2.2. Do the cuts fall between supervised, unsupervised and reinforcement learning? Notice that chunks can be very different lengths.

⚠️ Watch out

  • The notebook warns you may see a yellow DeprecationWarning because langchain-experimental is being retired. It's only a notice; the code still runs.
  • Semantic chunking costs embedding calls for every sentence at indexing time, and is slower. For a big library that adds up.
  • This article's lists ("- Classification: ...") have no full stops, so several list lines may be treated as one "sentence".

🌍 In real projects

Semantic chunking helps most with long text that has no headings: meeting transcripts, chat logs, scanned reports. When the document already has good headings, Part 2.4 is cheaper and usually just as good.

PART 2.4

Structure-based chunking: cut at the headings

Many documents already have sections. Cut there, and remember which heading each chunk came from.

chunking_strategies.ipynb · cell 9 · TODO 6: MarkdownHeaderTextSplitterruns locally
import textwrap
from langchain_text_splitters import CharacterTextSplitter

# textwrap.dedent removes the common left indentation so headings start with "#"
text = textwrap.dedent("""
    # Machine Learning Fundamentals

    Machine learning is a subset of artificial intelligence that enables computers to learn and improve from experience without being explicitly programmed.

    ## Types of Machine Learning

    ### Supervised Learning
    Supervised learning uses labeled training data to learn a mapping function from input to output. Common examples include:
    - Classification: Predicting categories (spam/not spam)
    - Regression: Predicting continuous values (house prices)

    ### Unsupervised Learning
    Unsupervised learning finds hidden patterns in data without labeled examples:
    - Clustering: Grouping similar data points
    - Dimensionality reduction: Reducing feature space

    ### Reinforcement Learning
    An agent learns through interaction with an environment, receiving rewards or penalties for actions taken.
""").strip()

# (a) Pure fixed length: separator="" means "cut anywhere", even in the middle of a word
naive_splitter = CharacterTextSplitter(chunk_size=100, chunk_overlap=0, separator="")
naive_chunks = naive_splitter.split_text(text)
print("Pure fixed-length (first 3 chunks) - notice the broken words:")
for chunk in naive_chunks[:3]:
    print("   ", repr(chunk))

💡 What is going on

  • headers_to_split_on is a list of pairs: the Markdown mark to look for, and the name to store it under. ("##", "Header 2") means "every line starting with ## starts a new chunk, and its text goes into metadata["Header 2"]".
  • Each chunk gets all the headings above it. The Supervised Learning chunk carries Header 1 = Machine Learning Fundamentals, Header 2 = Types of Machine Learning and Header 3 = Supervised Learning.
  • By default the heading lines themselves are removed from page_content and kept only in the metadata.
Stuck? One possible answer for TODO 6 (not in the notebook: try it yourself first)
possible answer · TODO 6your answer
markdown_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on)
md_header_splits = markdown_splitter.split_text(text)

✎ What to look for

Look at each Metadata: line. You should get one chunk per section, and each chunk should hold exactly one topic. Compare this with the fixed-length chunks from 2.2.

🌍 Why the metadata is gold

  • Filtering: "search only inside the Supervised Learning section".
  • Showing sources: the answer can say "from: Types of Machine Learning › Supervised Learning".
  • Context: you can put the headings back in front of the chunk before embedding, so a short chunk still "knows" what it's about.

⚠️ Watch out

Sections can be huge or tiny. A common recipe is two steps: cut at headings first, then run RecursiveCharacterTextSplitter on any section that is still too long. The headings stay in the metadata of every piece.

PART 2.5

HyDE: search with a fake answer

A shopper types "I want running shoes". The catalogue says "trainers", "sneakers", "Ultraboost". The words don't match. HyDE fixes that.

Step 1 · Keyword search without HyDE

💡 What is going on

  • BM25 is classic keyword search, the kind search engines used before AI. It gives a product a higher score when it contains the query's words, especially rare words, and it doesn't understand meaning at all.
  • Tokenizing means cutting text into words. Here it's just .lower().split(): lower-case, then split at spaces.
  • BM25Okapi(tokenized_products) builds the index: it counts which words appear in which product titles.
  • get_scores(...) returns one score per product. np.argsort(...)[::-1] lists product positions from best to worst score; the code keeps only scores above 0.1 and at most 3.

Query words: iwantrunningshoes

Catalogue words: sneakerstrainersmarathonshoesfootwearboots

Only one product title contains "shoes", and none contains "running". BM25 has almost nothing to match on.

✎ What to look for

Very few products (maybe only one, maybe none) come back. Real running products such as the Pegasus or Gel-Kayano trainers are missed because they don't share a word with the query.

⚠️ A sneaky detail: punctuation

.split() only splits at spaces, so punctuation sticks to words. If the LLM writes trainers, (with a comma), that token is trainers, and does not match trainers. If HyDE helps less than you expected, look for this. A small regex tokenizer (exercise 5) fixes it.

🔧 Analogy: asking a shop assistant

You say "something for running". A good assistant thinks "ah, Pegasus, Gel-Kayano, Ultraboost" and walks to the shelf with those labels. HyDE gives your search that assistant: the LLM translates the question into shelf-label words.

💡 The trade-offs in one breath

Smaller chunks are more precise but lose context. Bigger chunks keep context but blur the match. Overlap protects the edges but stores some text twice. Smarter cutting (semantic, headings) gives cleaner chunks but needs either money (embeddings) or structure (headings). HyDE finds more, at the cost of one LLM call, a little delay, and some risk, on every question.

?

When HyDE helps, and when it doesn't

Helps when…
  • Questions are short or vague ("running shoes", "my laptop is slow").
  • Users and documents use different words (shoppers vs catalogue, patients vs medical notes).
  • You use keyword search, or embeddings that match question-to-document poorly.
Hurts or wastes money when…
  • The query is already precise: a product code, an error message, a name.
  • The LLM doesn't know the topic (your company's private terms) and imagines the wrong words.
  • Every millisecond counts: one extra LLM call per question adds delay and cost.

⚠️ Never show the fake answer as the answer

The hypothetical answer may contain made-up facts and products. It is only a search key. The final answer must come from the real chunks that the search returns.

🌍 In real projects

Teams often search with both the plain question and the HyDE answer and merge the results, so a bad imagination can't hide good results. They also cache HyDE answers for common questions to save calls.

Quick quiz

1. In this notebook, what unit is chunk_size measured in?

Characters (letters, spaces and punctuation), not words or tokens.

2. Why does the code give each Chroma chunk an id like "150-0"?

So that running the cell again overwrites the same chunks instead of storing duplicates, which would fill the search results with copies.

3. What does separator="" do in CharacterTextSplitter?

It allows a cut anywhere, even in the middle of a word, so every chunk is exactly the chunk size (except the last).

4. Which two parts need an OpenAI key besides the HyDE step?

Storing and searching in Part 2.1 (OpenAI embeddings) and semantic chunking in Part 2.3 (it embeds every sentence).

5. What extra thing does MarkdownHeaderTextSplitter give you that the other splitters don't?

Each chunk's headings, stored in its metadata (Header 1, Header 2, Header 3), which you can use for filtering and for showing sources.

6. In HyDE, why do we ask the LLM for fake product titles instead of advice for the shopper?

Because we search with the LLM's text. Text that looks like the documents shares their words (or meaning), so it finds them. Advice would not look like a product title.

7. Name one case where HyDE is a bad idea.

When the query is already exact (a product code or error message), when the LLM doesn't know your private terms, or when the extra LLM call's delay and cost are too much.
